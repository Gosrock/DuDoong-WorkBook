# 통합 에러 핸들링 정책

> 최종 수정: 2026-03-15

---

## 1. 에러 응답 형식

모든 API 에러는 다음 구조로 응답합니다.

```
HTTP 상태 코드 + 에러 응답 본문
```

**에러 응답 본문 구조**

| 필드 | 설명 | 예시 |
|------|------|------|
| `code` | 도메인 에러 코드 | `ORDER_NOT_FOUND` |
| `message` | 사용자 노출 메시지 | "주문 정보를 찾을 수 없습니다." |
| `timestamp` | 에러 발생 시각 | `2026-03-15T10:00:00Z` |

---

## 2. HTTP 상태 코드 매핑 기준

| 상태 코드 | 의미 | 사용 기준 |
|-----------|------|-----------|
| `400 Bad Request` | 잘못된 요청 | 입력값 형식 오류, 필수 파라미터 누락, 비즈니스 규칙 위반 |
| `401 Unauthorized` | 인증 필요 | 로그인되지 않은 상태에서 인증 필요 리소스 접근 |
| `403 Forbidden` | 접근 권한 없음 | 로그인은 되었으나 해당 리소스에 대한 권한 없음 |
| `404 Not Found` | 리소스 없음 | 존재하지 않거나 삭제된 리소스 조회 |
| `409 Conflict` | 충돌 | 중복 요청, 이미 처리된 요청 (예: 중복 결제) |
| `422 Unprocessable` | 처리 불가 | 형식은 맞으나 비즈니스 로직상 처리할 수 없는 상태 |
| `500 Internal Server Error` | 서버 오류 | 예상치 못한 서버 내부 오류 |
| `503 Service Unavailable` | 서비스 불가 | 점검 중 또는 외부 서비스(PG사 등) 장애 |

### 400 vs 403 vs 404 선택 기준

- **400**: 요청 자체가 잘못됨 (형식, 값의 범위, 비즈니스 제약 위반)
- **403**: 요청은 유효하지만 이 사용자는 해당 작업을 할 권한이 없음
- **404**: 요청 대상 리소스가 존재하지 않음 (권한 없는 리소스도 404로 응답하여 존재 여부 노출 방지 가능)

## 3. 사용자 노출 메시지 톤앤매너

### 원칙

- **~할 수 없습니다** 형태 사용 (단정적이지 않고 안내하는 어조)
- **이유 + 대안** 구조로 작성
- 기술적 용어 사용 금지 (null, exception, timeout 등)
- 최대 2문장 이내

### 메시지 작성 패턴

```
[무엇을] [왜] ~할 수 없습니다. [대안/안내]
```

### 좋은 예 / 나쁜 예

| 나쁜 예 | 좋은 예 |
|---------|---------|
| "NullPointerException 발생" | "주문 정보를 찾을 수 없습니다. 이미 취소된 주문일 수 있습니다." |
| "403 Forbidden" | "해당 공연을 수정할 권한이 없습니다. 공연 주최자 계정으로 로그인해 주세요." |
| "결제 실패" | "결제를 완료할 수 없습니다. 카드 정보를 확인하거나 다른 결제 수단을 이용해 주세요." |
| "Timeout" | "요청 처리 시간이 초과되었습니다. 잠시 후 다시 시도해 주세요." |

## 4. 도메인별 주요 에러 코드

### Order (주문)

| 에러 코드 | HTTP | 사용자 메시지 |
|-----------|------|---------------|
| `ORDER_NOT_FOUND` | 404 | "주문 정보를 찾을 수 없습니다." |
| `ORDER_ALREADY_CANCELLED` | 409 | "이미 취소된 주문입니다." |
| `ORDER_CANCEL_PERIOD_EXPIRED` | 422 | "취소 가능 기간이 지나 취소할 수 없습니다. 고객센터로 문의해 주세요." |
| `ORDER_DUPLICATE` | 409 | "이미 처리된 주문입니다. 주문 내역을 확인해 주세요." |

| `ORDER_STOCK_EXHAUSTED` | 422 | "선택하신 티켓이 매진되었습니다. 다른 구역을 선택해 주세요." |

## 5. 에러 발생 시 사용자 경험 (UX)

### 에러 유형별 표시 방식

| 에러 유형 | 표시 방식 | 동작 |
|-----------|-----------|------|
| 입력 유효성 오류 (400) | 인라인 메시지 | 해당 입력 필드 하단에 메시지 표시 |
| 인증 만료 (401) | 모달 | "다시 로그인" 버튼 → 로그인 페이지로 이동 |
| 권한 없음 (403) | 토스트 or 리다이렉트 | 메시지 노출 후 이전 페이지로 이동 |
| 리소스 없음 (404) | 전용 404 페이지 | 홈으로 이동 버튼 제공 |
| 비즈니스 오류 (409/422) | 토스트 or 모달 | 메시지 노출, 재시도 또는 대안 안내 |
| 서버 오류 (500) | 토스트 | "잠시 후 다시 시도해 주세요" 메시지 |
| 서비스 불가 (503) | 전용 점검 페이지 | 예상 복구 시각 안내 (가능한 경우) |

### 결제 관련 에러 특별 처리

- 결제 실패 시: 주문 상태를 명확히 안내 (결제 미완료 / 취소 처리됨)
- 중복 결제 방지: 결제 버튼 비활성화 처리 후 응답 대기
- PG사 오류: "결제사 오류로 처리할 수 없습니다. 잠시 후 다시 시도해 주세요." 표시

## 6. 에러 로깅 기준

| 심각도 | 대상 에러 | 로깅 수준 |
|--------|-----------|-----------|
| Critical | 500 서버 내부 오류, 결제 오류 | ERROR + 알림(Slack) |
| Warning | 반복되는 4xx 오류, 외부 API 실패 | WARN |
| Info | 일반 비즈니스 오류 (404, 422 등) | INFO |

> 개인정보(이름, 이메일, 결제 정보 등)는 로그에 포함하지 않습니다.
