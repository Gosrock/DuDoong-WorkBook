# 주문/결제(Order) 도메인 정책

## 상태 머신

9개 상태, 11개 전이 규칙으로 구성됩니다.

```
                    ┌──────────────────────────────────────┐
                    │                                      │
              유료/무료선착순                          두둥/승인형
                    │                                      │
                    ▼                                      ▼
READY ──────► PENDING_PAYMENT                    PENDING_APPROVE
                    │                                      │
        ┌───────────┼────────────┐              ┌──────────┼──────────┐
        │           │            │              │                     │
  Toss확인     0원 무료확정    서버오류      관리자 승인          관리자 거절
        │           │            │              │                     │
        ▼           ▼            ▼              ▼                     ▼
     CONFIRM    APPROVED      FAILED        APPROVED             CANCELED
        │           │
        └─────┬─────┘
              │
     ┌────────┼────────┐
     │                  │
  사용자 환불      관리자 취소
     │                  │
     ▼                  ▼
   REFUND           CANCELED
```

| 상태 | 코드 | 설명 |
|------|------|------|
| 주문 생성 | `READY` | 초기 상태 |
| 결제 대기 | `PENDING_PAYMENT` | 유료/무료 선착순 주문 |
| 승인 대기 | `PENDING_APPROVE` | 두둥티켓/승인형 주문 |
| 결제 완료 | `CONFIRM` | PG 결제 확인 완료 |
| 승인 완료 | `APPROVED` | 관리자 승인 또는 무료 확정 |
| 환불 완료 | `REFUND` | 사용자 환불 |
| 취소됨 | `CANCELED` | 관리자 취소 또는 거절 |
| 결제 실패 | `FAILED` | 서버 오류 |
| 만료됨 | `OUTDATED` | 결제 시간 초과 (배치 처리) |

---

## 결제 방식 라우팅

티켓의 지불 유형과 승인 유형 조합에 따라 **자동** 결정됩니다.

| 지불 유형 | 승인 유형 | 처리 방식 | 주문 방식 코드 |
|-----------|-----------|----------|--------------|
| 유료 티켓 | 선착순 | 토스페이먼츠 PG 결제 | `NORMAL` |
| 무료 티켓 | 선착순 | 즉시 확정 (0원 결제) | `NORMAL` |
| 무료 티켓 | 승인형 | 관리자 승인 대기 | `APPROVAL` |
| 두둥 티켓 | 승인형 | 무통장입금 후 관리자 승인 | `APPROVAL` |

---

## 토스페이먼츠 결제 정책

> **현재 상태: 유료 결제(PRICE_TICKET) 미운영** — 세금 이슈로 인해 실제 유료 결제는 하지 않고 있습니다.

### 운영 현황

| 티켓 유형 | 결제 | 운영 여부 |
|-----------|------|-----------|
| 무료 티켓 (`FREE_TICKET`) | 0원 즉시 확정 | **운영 중** |
| 두둥 티켓 (`DUDOONG_TICKET`) | 계좌이체 (토스 없음) | **운영 중** |
| 유료 티켓 (`PRICE_TICKET`) | 토스페이먼츠 카드 결제 | **미운영** (세금 이슈) |

### 유료 결제 활성화 시 필요 사항

코드는 완성되어 있으며, 아래 설정만 교체하면 실제 결제가 동작합니다.

**백엔드 환경변수:**

| 환경변수 | 용도 | 현재 값 |
|----------|------|---------|
| `TOSS_PAYMENTS_KEY` | 토스 시크릿키 (API 인증) | 테스트키 (`test_sk_...`) |
| `TOSS_MID` | 토스 상점 ID | `gosroc9mwo` |

**프론트엔드 환경변수:**

| 환경변수 | 용도 |
|----------|------|
| `NEXT_PUBLIC_CLIENT_KEY` | 토스 클라이언트키 (결제 위젯 초기화) |

**유료 티켓 생성 제약:**
- 제휴 호스트만 유료 티켓(`PRICE_TICKET`) 생성 가능
- 최소 금액: 1,000원 이상
- 승인 유형: 선착순(`FIRST_COME_FIRST_SERVED`)만 허용

### 유료 결제 플로우 (활성화 시)

```
관객: 예매하기 클릭
  → 서버: 주문 생성 (READY → PENDING_PAYMENT)
  → 프론트: 토스 결제 위젯 렌더링 (카드 결제)
  → 사용자: 카드 정보 입력 + 결제
  → 토스 → 프론트: /pay/confirm 리다이렉트 (paymentKey, orderId, amount)
  → 프론트 → 서버: 결제 승인 요청
  → 서버: 금액 검증 + 토스 API 최종 승인
  → 결제 완료 (PENDING_PAYMENT → CONFIRM)
```

**결제 승인 시 서버 검증 (5단계):**
1. 주문 소유자 확인
2. 결제 타입 확인 (NORMAL 방식인지)
3. 요청 금액 = 서버 금액 일치 확인
4. 동시 요청 방지 (분산락)
5. 토스 API 최종 승인 호출

## 주문 생성 시 검증 규칙

관객이 티켓을 주문하면, 시스템은 다음 **6가지 조건을 순서대로** 확인합니다. 하나라도 충족하지 못하면 주문이 거부됩니다.

### 1. 공연이 오픈 상태인가?

해당 이벤트가 현재 "진행중(OPEN)" 상태여야 합니다. 아직 준비 중이거나, 이미 종료/삭제된 공연에는 주문할 수 없습니다.

### 2. 공연 시작 전인가?

현재 시각이 공연 시작 시간보다 이전이어야 합니다. 공연이 이미 시작되었다면 더 이상 티켓을 구매할 수 없습니다.

### 3. 재고가 남아있는가?

주문하려는 수량만큼 티켓 재고가 남아있어야 합니다. 예를 들어 남은 재고가 2장인데 3장을 주문하면 거부됩니다.

### 4. 한 종류의 티켓만 주문하는가?

하나의 주문에는 **한 가지 종류의 티켓만** 담을 수 있습니다. 예를 들어 "일반석"과 "VIP석"을 같은 주문에 섞어서 구매할 수 없습니다. 다른 종류를 원하면 별도로 주문해야 합니다.

### 5. 1인당 구매 제한을 넘지 않는가?

호스트가 설정한 1인당 최대 구매 수량을 초과할 수 없습니다. 이 검사는 **이전에 이미 구매한 수량**을 포함하여 계산합니다.

> 예: 구매 제한이 4장인 티켓을 이전에 2장 구매한 사용자는 추가로 최대 2장만 주문 가능합니다.

### 6. 옵션이 중간에 변경되지 않았는가?

관객이 장바구니에 담은 시점과 실제 주문을 생성하는 시점 사이에 호스트가 옵션 구성을 변경했는지 확인합니다. 변경이 감지되면 주문을 거부하고 관객에게 다시 옵션을 선택하도록 안내합니다.

## 승인형(두둥 티켓) 주문의 추가 검증

두둥 티켓이나 승인형 무료 티켓처럼 호스트가 직접 승인하는 방식의 주문은 **2가지 추가 검증**을 거칩니다. 일반 결제 주문보다 더 보수적으로 검사하는 이유는, 승인 대기 중인 주문들이 아직 확정되지 않은 상태에서 재고와 구매 제한을 미리 잡아두어야 하기 때문입니다.

### 승인 대기 포함 재고 검사

현재 "승인 대기 중"인 모든 주문의 수량을 합산한 뒤, 거기에 새 주문 수량을 더했을 때 전체 재고를 넘지 않아야 합니다.

> 예: 총 재고 100장, 현재 승인 대기 주문 80장이면 → 새 주문은 최대 20장까지만 가능합니다.

### 승인 대기 포함 구매 제한 검사

해당 사용자가 이미 구매한 티켓 수 + 승인 대기 중인 주문 수 + 새 주문 수를 모두 합산하여 구매 제한을 검사합니다.

> 예: 구매 제한 4장, 이미 구매 1장, 승인 대기 2장이면 → 새 주문은 최대 1장만 가능합니다. "이미 신청한 주문이 승인될 때까지 기다려주세요"라는 메시지가 표시됩니다.

## 결제 확인 시 검증 규칙

관객이 토스페이먼츠에서 카드 결제를 완료하고 돌아오면, 시스템은 주문을 최종 확정하기 전에 다시 검증합니다.

1. **결제 주문이 맞는지**: 승인형 주문이 실수로 결제 확인 경로로 들어오는 것을 차단합니다.
2. **결제 대기 상태인지**: 이미 처리된 주문이 중복으로 확인되는 것을 방지합니다.
3. **PG 결제 금액과 주문 금액이 일치하는지**: 토스페이먼츠에서 실제로 결제된 금액이 시스템의 주문 금액과 다르면, 결제를 거부하고 자동으로 환불 처리합니다.
4. **전체 재검증**: 주문 생성 시점과 결제 완료 시점 사이에 상황이 바뀌었을 수 있으므로, 이벤트 상태/재고/옵션 등을 **다시 한번** 검사합니다. 이 재검증 덕분에 결제 도중 재고가 소진되거나 이벤트가 닫힌 경우에도 안전하게 처리됩니다.

---

## 주문 승인 시 검증 규칙

호스트가 두둥 티켓 주문을 승인할 때 다음을 확인합니다.

1. **승인형 주문이 맞는지**: 카드 결제 주문을 승인하려는 시도를 차단합니다.
2. **승인 대기 상태인지**: 이미 승인/거절된 주문의 중복 처리를 방지합니다.
3. **전체 재검증**: 승인 시점에 이벤트가 아직 진행 중이고, 재고가 남아있는지 등을 다시 확인합니다.
4. **사용자가 탈퇴하지 않았는지**: 승인 대기 중에 관객이 탈퇴한 경우, 해당 주문은 승인이 거부됩니다. 이미 존재하지 않는 사용자에게 티켓을 발급하는 것을 방지하기 위함입니다.

---

## 무료 주문 확인 시 검증 규칙

무료 선착순 티켓의 경우, 결제 없이 바로 확정됩니다. 이때:

1. **실제로 무료 주문인지**: 결제 금액이 0원이 아닌 주문이 무료 확인 경로를 타는 것을 차단합니다.
2. **결제 대기 상태인지**: 이미 처리된 주문의 중복 확인을 방지합니다.
3. **전체 재검증**: 마찬가지로 이벤트 상태, 재고 등을 다시 확인합니다.

---

## 취소/환불 시 검증 규칙

### 환불 (관객이 직접)

관객이 마이페이지에서 환불을 요청하면:

1. **본인의 주문인지**: 다른 사람의 주문을 환불할 수 없습니다.
2. **환불 기한 내인지**: 공연 시작 시간이 지나면 환불이 불가능합니다. 공연이라는 상품 특성상 시작 후에는 가치가 소멸하기 때문입니다.
3. **환불 가능한 상태인지**: "결제 완료" 또는 "승인 완료" 상태의 주문만 환불할 수 있습니다. 아직 결제 대기 중이거나 이미 취소된 주문은 환불 대상이 아닙니다.
4. **이벤트가 아직 진행 중인지**: 정산이 시작되었거나 종료된 이벤트의 주문은 환불할 수 없습니다.

환불이 처리되면 쿠폰 복구, 티켓 취소, 재고 복구, PG 환불이 **자동으로** 이루어집니다.

### 취소 (호스트가)

호스트가 관리 화면에서 주문을 취소할 때도 동일한 검증을 거칩니다. 단, 본인 확인 대신 호스트 권한(매니저 이상)을 확인합니다.

### 거절 (승인 대기 주문)

호스트가 승인 대기 중인 주문을 거절하는 것은 비교적 단순합니다. 해당 주문이 "승인 대기" 상태인지만 확인하면 됩니다. PG 결제가 없었으므로 환불 처리도 불필요합니다.

## 주문 관련 에러 메시지 목록

문의 대응 시 사용자에게 표시되는 에러 메시지와 원인을 정리합니다.

| 사용자에게 보이는 메시지 | 원인 | 대응 |
|------------------------|------|------|
| "본인의 주문이 아닙니다" | 다른 사용자의 주문에 접근 | 로그인 계정 확인 |
| "올바르지 않은 주문입니다" | PG 결제 금액과 주문 금액 불일치 | 재주문 안내 |
| "결제,승인 대기중인 주문이 아닙니다" | 이미 처리된 주문에 중복 요청 | 주문 상태 확인 안내 |
| "주문을 취소할 수 없는 상태입니다" | 결제/승인 완료가 아닌 주문 취소 시도 | 현재 주문 상태 안내 |
| "주문을 환불할 수 없는 상태입니다" | 결제/승인 완료가 아닌 주문 환불 시도 | 현재 주문 상태 안내 |
| "환불을 할 수 있는 기한을 지났습니다" | 공연 시작 후 환불 시도 | 공연 시작 전까지만 환불 가능 안내 |
| "무료 주문이 아닙니다" | 유료 주문이 무료 경로로 진입 | 시스템 오류, 재주문 안내 |
| "최소 결제금액인 1000원보다 낮은 주문입니다" | 유료 티켓 가격이 1,000원 미만 | 호스트에게 가격 수정 요청 |
| "장바구니에 아이템을 담는 정책을 위반하였습니다" | 여러 종류 티켓 혼합 주문 | 한 종류씩 따로 주문 안내 |
| "주문 과정중 아이템의 옵션이 변화했습니다" | 주문 중 호스트가 옵션 변경 | 새로고침 후 재주문 안내 |
| "유저가 탈퇴를 했습니다" | 탈퇴 사용자 주문 승인 시도 | 해당 주문 거절 처리 안내 |
| "승인 대기중인 주문으로 인해 구매 제한 초과" | 이미 신청한 주문이 있어서 추가 불가 | 기존 주문 승인 대기 안내 |

## 동시성 제어

- 동일 사용자가 동시에 여러 주문을 생성하는 것을 차단합니다 (사용자 ID 기반 분산락).
- 결제 확인 시 토스페이먼츠에서 받은 금액과 주문 금액을 일치 검증합니다.

## 주문 생성 경로 (3가지)

### Case 1: 일반 주문 (결제)

유료 또는 무료 선착순 티켓 주문 시 결제 대기 상태로 생성됩니다.

### Case 2: 쿠폰 적용 주문

쿠폰을 적용하여 유료 주문을 생성합니다. 쿠폰 최소 결제액을 충족해야 하며, 결제 대기 상태로 생성됩니다.

### Case 3: 승인 주문 (두둥 티켓) — `APPROVAL`

두둥 티켓 또는 승인형 무료 티켓 주문 시 승인 대기 상태로 생성됩니다.

---

## 결제 금액 계산

```
공급 금액  = 상품 가격 합계 (티켓 가격 × 수량 + 옵션 추가금)
할인 금액  = 쿠폰 할인액
실 결제 금액 = 공급 금액 - 할인 금액
```

## 취소/환불 정책

### 3-way 분리

| 구분 | 주체 | 대상 상태 | 결과 상태 |
|------|------|----------|----------|
| **환불** | 사용자 | 결제 완료, 승인 완료 | 환불 완료 |
| **취소** | 관리자 | 결제 완료, 승인 완료 | 취소됨 |
| **거절** | 관리자 | 승인 대기 | 취소됨 |

### 환불 가능 조건
- **공연 시작 전**에만 환불/취소 가능
- 취소 수수료 **없음**
- 사용자 본인 확인 필요

### 환불 시 자동 처리
1. 쿠폰 사용 복구
2. 발급 티켓 취소
3. 재고 복구
4. 유료 주문의 PG 환불 (비동기)

### 결제 확인 실패 시 자동 처리
결제 확인 중 오류 발생 시 롤백 단계에서 자동으로 다음을 처리합니다:
1. 쿠폰 사용 취소
2. 발급 티켓 철회
3. PG 환불 요청

## 티켓별 환불 규정 (노션 가이드)

> 출처: [두둥 환불 규정 관련](../public-notion/두둥-환불-규정-관련.md)

| 티켓 종류 | 환불 방법 | 비고 |
|-----------|----------|------|
| 무료 티켓 | 마이페이지에서 직접 환불 | 공연 시작 전까지 |
| 유료 티켓 | 마이페이지에서 직접 환불 (PG 자동 환불) | 공연 시작 전까지 |
| 두둥 티켓 | 마이페이지에서 환불 요청 → **주최자에게 별도 연락하여 계좌 전달** | 주최자가 직접 환불 의무 |

> 공연이라는 상품의 특성상 공연이 종료되면 상품 가치가 소멸합니다.

## 주문번호 규칙

- 주문번호 형식: `"R"` + 오프셋(10,000) + 주문 ID
  - 예: order_id=1 → R10001
- 주문이 저장되는 시점에 자동 생성됩니다.
- 주문 생성 시 Slack 알림이 발송됩니다.
